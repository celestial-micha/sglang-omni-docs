# 一批任务至少有多少条才启动异步解码：async_lookahead_min_batch_size

## 1. 验证对象与结论

语音识别服务收到人声后，会分步生成文字，这叫“解码”。异步解码可以让这些步骤交错处理。本参数要控制的是：服务实际凑成的一批任务，至少有多少条，才启动异步解码。例如门槛设为 2，实际一批只有 1 条就不启动；实际一批达到 2 条就启动。

三类判定：① NPU 需要，门槛功能和所测配置的性能对照均已完成。开启异步后没有新增失败或转写差异，但三轮速度有波动，不能声称稳定加速；结论不外推到所有模型和配置。

之所以出现两个名字，是因为任务清单和报告文件名写作 `async_lookahead_min_batch_size`，而所查代码、配置字段和本次实验实际使用的都是 `async_decode_min_batch_size`。现有材料不能证明前一个名字曾是可用的配置字段，更不能据此说软件后来“改名”；配置时请使用实际字段 `async_decode_min_batch_size`。

实测中，门槛 2 对实际批次 1、2、3 分别表现为不启动、启动、启动；门槛 4 对实际批次 3、4 分别不启动、启动。关闭异步总开关时，即使达到门槛也不启动。所有请求都返回了正确的识别文字。因此，“门槛是否控制启动”这个问题，在这套 NPU 服务和这些边界上已验证。它不证明异步一定更快，也不代表所有模型都已分别测试。

## 2. 测试用例

实验道理：先保持语音和模型不变，让实际批次落在门槛的下面与正好相等的位置；只改变门槛或请求批次，观察服务是否真的启动异步，并同时检查文字结果。必须读取服务记录的“实际批次”，因为同时提交 4 条请求，服务不一定会把 4 条放进同一批。

### 2.1 环境信息

在 151 节点的物理 NPU 13 上运行 Qwen3-ASR-0.6B，使用 SGLang-Omni 0.1.6、SGLang 0.5.19。各组输入是同一段人声，正确文字为 “Get the trust fund to the bank early.”。服务端增加了只记录判断和启动事件的日志，没有改动门槛判断规则。记录中的 `actual_batch` 是实际批次，`lookahead` 是本轮是否决定使用异步，`CODEX_ASYNC_LAUNCH` 表示真正启动。

原始核查材料在 `七参数_实验证据_20260923` 和 `七参数_实验证据_20260924` 目录：服务日志 `async_qwen_t2.log`、`async_qwen_t4.log`、`async_qwen_off_t2.log`、`async_t2_n3_20260924.log`，对应请求结果为 `async_t2_n1.json`、`async_t2_n2.json`、`async_t2_n3_20260924.json`、`async_t4_n3.json`、`async_t4_n4.json`、`async_off_t2_n2.json`。读懂本报告不需要先打开这些文件。

性能补测使用同节点物理 NPU 1、Qwen3-ASR-0.6B，两组均开启异步总开关，只将门槛设为 2 或 5；图捕获关闭、CPU 卸载为 0、`max_total_tokens=8192`。同一清单的 20 条音频校验源 SHA 后转为 16 kHz 单声道 WAV，两组 WAV 的 SHA 一致。每组先以 4 条独立预热，再按固定顺序每批并发 4 条，共测 3 轮、60 条正式请求。原始材料在工作区 `交付补测_20260929/parallel_evidence_0324/async_perf_t2`、`async_perf_t5` 及对应服务日志、YAML；独立复核结果为 `交付补测_20260929/async_performance_independent_audit.json`。

### 2.2 用例测试结果

| 用例名称 | 用例步骤 | 预期结果 | 实际结果 |
| --- | --- | --- | --- |
| 少于门槛 2 | 门槛设为 2，提交 1 条人声，核对实际批次和文字 | 实际批次为 1，不启动异步，仍返回文字 | 实际批次 1，没有异步启动；请求 HTTP 200，转写正确 |
| 正好达到门槛 2 | 门槛仍为 2，并发提交 2 条，核对服务实际批次 | 实际批次为 2，启动异步，两条都正确返回 | 实际批次 2，记录到异步启动；两条均 HTTP 200，转写正确 |
| 超过门槛 2 | 门槛仍为 2，并发提交 3 条，并持续查看服务实际批次 | 实际批次为 3 时启动异步；若随后批次降为 1，应停止启动 | 实际批次 3 时记录到异步启动，随后批次降为 1 时判断为不启动；三条均 HTTP 200，转写正确 |
| 少于门槛 4 | 门槛设为 4，并发提交 3 条 | 实际批次为 3，不启动异步，三条仍正确返回 | 实际批次 3，判断为不启动；三条均 HTTP 200，转写正确 |
| 正好达到门槛 4 | 门槛仍为 4，并发提交 4 条 | 实际批次为 4，启动异步，四条都正确返回 | 实际批次 4，记录到异步启动；四条均 HTTP 200，转写正确 |
| 总开关关闭 | 门槛设为 2，再设 `enable_async_decode=false`，提交 2 条 | 即使达到门槛也不启动异步，两条仍完成 | 日志没有异步启动事件；两条均 HTTP 200，转写正确 |
| 同输入性能对照 | 门槛 2/5 各预热后运行同 20 条、并发 4、重复 3 轮，同时核实际分支 | 请求完成、输出可逐条比较，并记录耗时；不预设一定加速 | 两组各 60/60 完成，逐条转写完全一致；每轮均为 216 个参考词、2 次词编辑。门槛 2 三轮耗时 2.935/2.940/2.647 秒，门槛 5 为 2.849/2.546/4.542 秒 |

原六组分别检查了低于、等于、高于门槛，以及批次变化和总开关优先级，功能证据保留。性能补测日志另确认：门槛 2 在实际批次 4/3/2 时分别成功启动异步 221/48/21 次，批次 1 时不启动；门槛 5 的实际批次 1–4 均不启动。以上分支累计数包含预热，不能当作正式请求数。

表中每轮耗时是五批客户端组耗时之和，排除转码及批间间隔，包含少量客户端记录与线程收尾。两组全部正式请求的平均 HTTP 延迟分别为 0.517 秒和 0.599 秒；按组耗时计算的吞吐分别为 7.04 和 6.04 请求/秒。门槛 5 第三轮明显较慢，同机还有其他任务，现有证据不能把波动归因于门槛；前两轮反而是门槛 5 更快，因此不以合计均值宣称稳定收益。未测请求取消和长期高并发，不对此作结论。

## 3. UT覆盖

### 3.1 当前覆盖情况

UT（单元测试）检查代码规则：批次小于门槛不启动，达到门槛启动，批次变化后重新判断；还检查当前参数名的配置传递和门槛必须为正数。运行 `test_async_decode.py` 与 `test_engine_factory.py`，整套结果为 57 项通过、3 项跳过；跳过项是 CUDA 专属测试，不能算作 NPU 通过。57 是两套测试的合计，不是本参数独占的数量。

UT 不能证明真实服务会凑出预期批次，也不能证明请求最终得到正确文字；第二节的 NPU 请求已检查这两件事。请求取消、长期高并发若列入后续验收，应另做真实服务测试，不能靠增加同类 UT 代替。
